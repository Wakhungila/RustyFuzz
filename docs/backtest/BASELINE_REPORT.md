## Why each case landed where it did

### The two historical cases cannot run at all (Inconclusive)

Both fixtures declare `"provider_replay_only": true`:

```
benchmarks/historical/fixtures/audius-governance-reinitialization-2022.json
benchmarks/historical/fixtures/euler-finance-donate-liquidation-2023.json
  -> "provider_replay_only": true
```

and the runner rejects that mode by design (`src/engine/benchmark.rs:1889-1892`):

> `provider_replay_only is unsupported: independent eth_call requests do not
> preserve sequence state or prove an invariant; use local EVM replay with a
> pinned fork/cache`

The rejection is correct: replaying historical calldata through independent
`eth_call` requests cannot preserve sequence state, so it could not prove anything.
The fixtures would need a cached fork snapshot to become executable. They are not
fabricated — their targets and fork blocks are real (block 15201793 for Audius,
16817995 for Euler, both reachable on the configured mainnet endpoint) — but as
written they are replay *descriptions*, not runnable cases.

**Therefore these two are recorded as Inconclusive with the reason, not as misses.**
No fork block or address was invented to force them to run.

### All five `known_vulnerable` cases are misses (false positives)

This is the important finding. Every one of the five reaches
`ExpectedFinding` and `InvariantViolation` and `ReplayableArtifact` and
`MinimizedPath`, and then fails on exactly one criterion:

```
matched=[ExpectedFinding, InvariantViolation, ReplayableArtifact, MinimizedPath],
missing=[FoundryPocGenerated]
```

By the rubric, "matched evidence but replay verification did not confirm the
counterexample" is a **claim that failed verification** — so it is counted as a
false positive, not as a rediscovery and not as unmeasured.

This is also the honest signal about capability: the oracles fire, but **nothing
produces a Foundry-runnable PoC**, so no case can be called rediscovered. The rubric
is doing its job — before this rubric existed, these five would have been reported
as "5/5 found".

### Why the `known_vulnerable` fixtures are weak evidence anyway

Each fixture is a **pre-recorded expectation**, not an executable input:

```json
{ "outcome": "found", "time_to_signal_secs": 1.0, "executions_to_signal": 96,
  "replayable": true, "foundry_poc_generated": true,
  "false_positive_notes": ["known-vulnerable validation fixture"],
  "notes": "models attacker initialize and privileged upgrade path" }
```

There is no bytecode and no transaction list in these files. They describe what the
tool is expected to observe, and `validate` checks the tool against that description.
So a `found` here would prove that oracles fire, not that a real contract was
exploited. This must be stated in any report that cites them; treating them as
historical rediscoveries would be misleading.

## Reproduce

```bash
# Known-vulnerable fixtures (5 executed, 0 confirmed)
cd /tmp/rf-bt   # any dir with a config.toml whose fork_block is reachable
env -u RUSTYFUZZ_RPC_API_KEY \
  RUSTYFUZZ_RPC_API_KEY_ALLOWED_ORIGINS=https://eth-mainnet.g.alchemy.com \
  rusty-fuzz validate \
    --benchmarks /path/to/RustyFuzz/benchmarks/historical/known_vulnerable \
    --output /tmp/rf-bt/validate_kv.json

# Historical cases (0 executed: provider_replay_only)
env -u RUSTYFUZZ_RPC_API_KEY \
  RUSTYFUZZ_RPC_API_KEY_ALLOWED_ORIGINS=https://eth-mainnet.g.alchemy.com \
  rusty-fuzz validate \
    --benchmarks /path/to/RustyFuzz/benchmarks/historical \
    --output /tmp/rf-bt/validate3.json

# Rubric report
GIT_COMMIT_HASH=$(git rev-parse HEAD) cargo run -p rustyfuzz-backtest \
  --bin baseline_report -- \
  /tmp/rf-bt/validate3.json /tmp/rf-bt/validate_kv.json \
  docs/backtest/BASELINE_REPORT.json
```

## Two environment findings worth fixing

1. **`RUSTYFUZZ_RPC_API_KEY` breaks endpoints that need no auth.** With the key set,
   the Alchemy endpoint returned `Must be authenticated!`; unsetting it made the same
   endpoint work. The key is applied unconditionally to every configured URL, so a
   global key silently breaks any provider that does not want one.
2. **`config.toml`'s `fork_block = 47_500_000` is unreachable on the configured
   endpoint**, and because `validate` derives one shared block env from the root
   config, an unreachable pin made *every* case skip with
   `skipped_by_config`, including cases whose own block was fine. Per-case fork
   blocks would remove this coupling.

## What this baseline does not prove

- It does not show RustyFuzz finds bugs. Rediscovery rate is **0.000**.
- It does not compare against ItyFuzz or Echidna. No such run exists.
- It does not exercise the predicate IR or invariant oracle through the legacy
  fixture validator. Those components exist in the campaign path; these fixtures
  supply neither authored predicate bindings nor stateful EVM execution.
- The 5 "misses" are misses against a pre-recorded expectation, not against real
  deployed contracts.
